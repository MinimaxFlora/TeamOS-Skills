# 接口、后端与数据

涉及接口契约、持久化、并发写入、队列或第三方回调时读取相应小节。使用项目现有协议与数据层；选择实现前先找到实际调用方、权限判断、存储约束和失败处理。

## 契约跟随数据流

- 把输入、校验、业务处理、落库、响应串起来检查。字段缺失与空值、金额单位与精度、时区、枚举、分页排序都要在两端一致；修改契约时同时检查旧客户端和后台任务。
- 身份认证之后仍要验证对象归属、租户范围和操作权限；不能只信任客户端传来的用户 ID。查询使用参数绑定，动态字段或排序列采用受控映射。
- 为调用方保留可判定的错误语义。分页使用稳定排序与唯一兜底键；持续变动的数据集需要评估游标语义，不能只验证第一页。

## 并发与副作用

先写清不变量，例如余额不为负、同一订单只入账一次，再选原子条件更新、行锁或版本检查；检查影响行数，并处理冲突。普通事务内“先读再扣”仍可能竞争，事务存在本身不能证明正确；隔离级别与数据库行为须按实际版本核验。[事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)

幂等键须有明确的主体、操作范围和保留期；唯一约束防住同时到达的请求，同键不同业务参数应拒绝。单库操作将去重状态、业务变更与结果放进同一事务；重复请求返回已保存结果或明确的处理中状态，不能只用进程内集合去重。

外部扣款、发消息等不能靠本地事务自动撤销。复用供应商支持的幂等标识，设计持久化任务或事务发件箱、重试与对账；超时表示结果未知，先按原标识查询或安全重试，不能换单号重做。[幂等请求示例](https://docs.stripe.com/api/idempotent_requests)

支付回调按供应商协议验签，核对商户、订单、金额、币种与允许的状态变化；业务去重不能只依赖事件 ID。考虑重复、乱序及“处理成功但响应丢失”；确认事件已可靠保存或处理后再成功应答。客户端支付成功页面不能独立触发入账。[回调行为说明](https://docs.stripe.com/webhooks)

## 检查真实边界

按改动选择越权、非法输入、并发争抢、重复请求、提交后超时等反例，并同时核对响应与最终数据。事务、约束和锁的验证使用对应数据库，内存替身不能证明这些行为。队列检查重试上限、失败去向和重启恢复；查询优化检查真实参数与执行计划，索引命中本身不等于更快。

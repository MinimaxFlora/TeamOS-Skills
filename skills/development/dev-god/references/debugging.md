# 定位与修复

用于错误结果、异常、失败测试、性能异常或反复修不好的问题。需要修复时，诊断结论是执行过程的一部分，不是新的停工点。

## 建立可区分原因的证据

确认实际输入、预期结果、现象、环境和代码版本，找到最短真实复现路径。已有失败先分类：导入/依赖错误不能证明业务缺陷；预期失败的复现测试也不是“修复又失败了一轮”。

按可观察差异选择下一步：

| 不确定点 | 有用动作 |
| --- | --- |
| 错发生在何处 | 缩小到入口、边界、状态变化或最小调用 |
| 环境还是实现 | 比较实际配置/版本/输入，用隔离调用排除环境因素 |
| 同步还是竞态 | 固定输入与时序，检查旧请求、取消、重复和并发路径 |
| 错误有时消失 | 保留失败样本与运行条件，检查缓存、随机性和资源生命周期 |
| 已改仍失败 | 对照修复假设与最新输出，确认运行的确是新代码/新产物 |

维护少量仍能被证伪的候选原因，每次验证尽量区分它们。不要一次修改多个无关变量后凭偶然通过确定根因；排除原因也记录对应证据。

## 修复应改变失败机制

补判空前先确认值的业务含义；加重试前确认操作是否可重复；吞异常前确认错误的处理责任。移除校验、固定返回值、强制清缓存或增加巨大延时，只有需求本来如此且证据支持才可能是正确方案。

把失败样本转换为有独立预期的回归验证：先证明旧行为有问题，再确认修复后结果及相关边界。无法执行旧版本时如实说明，不能补造“修复前失败”日志。测试用例本身有错时，引用契约修正，而非禁止一切测试修改。

## 收敛与恢复

持续观察“已确认事实、已排除原因、仍未知的范围”。同一路径不能提供新信息时，改为调用链、数据流、配置、运行产物或最小实验取证。工具不存在、日志拿不到或外部服务不可访问时，完成其余可行动工作，交接具体缺口。

临时探针只保留有维护价值的部分；移除影响行为的探针后复验目标路径。结束时区分确认根因与暂时缓解，不把偶发不再出现说成完全修复。

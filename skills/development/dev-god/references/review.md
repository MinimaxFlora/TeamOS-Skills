# 代码审查

先确定审查对象：一个 diff、提交、模块、运行故障或整体设计。范围外背景只读到足以判断影响；不要为了展示工作量扩大审查。

## 追踪真实风险

- 从变更及受影响调用方出发，找能描述触发条件和后果的问题。优先数据损坏、越权、结果错误、状态竞争、资源泄漏、兼容性和明显性能退化。
- 权限与归属逐个请求核对，不能只看 UI 隐藏或某个入口做了鉴权。路径检查比较真正的边界，不用字符串前缀冒充目录包含关系。
- 读完整的相关分支，检查空值、零值、异常、取消、重试、异步旧结果、新旧格式及并发。结合现有测试，先找出覆盖不到的行为。
- 实际值流优先于函数名和注释。静态扫描提示是线索，缺少来源和调用上下文时不能直接判漏洞。

只读审查可以运行不修改源码、无外部副作用的复现或隔离检查；需要写验证材料时放临时目录，最终保持目标源码和原有改动不变。明确要求“审查并修复”则在目标范围内继续修复并验证。

## 发现如何写

每项说明：位置、触发条件、错误行为、实际影响、支持证据。需要时附最小复现；推测标明缺哪条证据。阻断级别根据影响和可触发性决定，不因“看起来不规范”就升为严重问题。

修复建议优先改变根因，同时说明必要兼容范围。风格、命名和抽象偏好只在用户要求或导致具体问题时提出；不凑固定数量，不把所有 lint 提示列成独立发现。

没有发现时说明检查过的范围与剩余盲点；“未发现明确问题”不等于证明全部安全或没有缺陷。

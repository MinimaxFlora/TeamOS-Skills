# 架构、迁移与性能

涉及模块边界、技术选型、兼容迁移或性能目标时读取对应部分。先看现有系统怎样运行、谁在调用、数据归谁管理，再决定是否改变结构。局部修复不必附带架构升级。

## 只解决当前的约束

明确限制来自哪里：实测瓶颈、维护困难、部署环境还是业务规则。对有实质取舍的决策，比较现状的小改方案与一个合理替代，说明收益、维护成本、失败方式和退出条件；单一清晰实现无需凑候选。

性能或兼容性是关键未知时，先做能回答该问题的小实验。新增缓存须明确失效与容量策略，新增队列须说明积压与重复处理，拆服务须说明数据一致性及独立部署的实际收益；减少几行代码不足以抵消长期运维成本。

## 迁移覆盖旧状态与混合版本

- 枚举生产者、消费者、存量数据、缓存、任务和外部客户端，追踪读写两端；不能只改当前调用路径。重构先保留可观察行为，再单独处理业务变化。
- 滚动升级时安排兼容顺序：先允许新旧格式共存，再分批迁移和切换读写，最后移除旧路径。双写需要失败补偿和核对，不能默认两边总会同时成功。
- 数据回填采用可恢复进度与幂等批次，依据锁等待、吞吐和负载调整批量；评估 DDL 的实际锁行为。用总量、约束和业务聚合校验覆盖范围，抽样用于补充内容检查。
- 回滚代码不等于回滚数据。验证旧版本能否读取新数据；不可逆转换保留恢复依据或前向修复路径。删除兼容代码以前，确认旧调用方确实退出。

## 性能结论来自可比测量

先记录输入规模和分布、代码版本、运行环境、并发模型及冷暖状态，测出修改前基线。按用户问题选择响应延迟、吞吐、内存、耗电或启动耗时；定位时间花在 CPU、数据库、网络还是等待后，再改最相关的路径。

使用相同数据与条件比较修改前后，重复次数由噪声决定，保留原始结果与分布。服务负载同时看尾延迟、错误率和吞吐；样本不足时不报精确分位数。区分运行时分配与进程常驻内存，不能把某一种采样值直接称为峰值内存。

优化后复核正确性、资源代价和目标边界。少做工作、改变精度或缓存旧结果导致的“提速”必须符合原契约。只有函数基准时不外推系统容量；没有修改前数据时报告当前测量，性能改进仍是待验证假设。

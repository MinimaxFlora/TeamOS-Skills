# 实现与契约

功能、接口、脚本、联调和文档任务使用本页。新项目确定最小可运行目标；已有项目围绕当前入口修改，不另建一套绕开原实现。

## 从目标到完整路径

- 把需求变成输入、结果和不可破坏的条件。例如“导出筛选结果”涉及筛选来源、数据范围、编码与文件内容，而不仅是一个下载按钮。
- 跟踪入口到结果的路径：输入组件/调用方 → 参数与校验 → 业务处理 → 状态或持久化 → 返回值 → 用户可见结果。只展开与本次变化有关的节点。
- 接口字段、单位、时区、标识、排序、缺省值和空值具有业务含义。区分字段缺失、空字符串、0、false、空集合；不能用统一 truthy 判断替代契约。
- 修改读写契约时找出所有生产者和消费者，包括早退、异常路径、缓存、导出、序列化、旧客户端及测试替身。明确是否需要向后兼容，再决定适配、迁移或同步变更；不要保留没有用途的双格式。

## 实现与联调

优先沿用工程内已有组件、封装和依赖。看到相似代码先核对职责和行为，再复用；不要机械把局部流程抽成通用框架。新增能力应能从真实入口到达，避免只有新函数、未接线的按钮、未注册路由或只更新类型定义。

外部服务尚不可用时，可用明确标注的替身验证内部边界，但保留真实适配路径和未验证项；不能让演示数据成为默认生产行为。错误和空状态必须与业务结果一致，不能把异常统一转换为成功或空列表。

配置变更核对实际生效位置与优先级。生成文件从源头改，再生成；不要直接编辑下一次构建就会覆盖的文件。文档记录真实命令、配置名称及行为边界，不能根据想象写“已支持”。

## 算法与可验证性

涉及递归、图、并发、数值或状态机时，先写出这次算法依赖的关键不变量和终止条件，选择能推翻错误实现的输入。不要求所有业务代码套形式证明。计数、去重、边界、溢出和资源释放按具体算法检查。

验收从需求或独立依据得出，避免把实现复制一遍当作测试期望。修完后查看完整 diff，确认无孤立实现、无漏改契约，也没有覆盖任务开始前的用户修改。
